= Contributing and releasing

Camel Kit is developed at https://github.com/apache/camel-kit[apache/camel-kit] under the Apache Camel project.
Workflow examples and migration samples live in
https://github.com/luigidemasi/camel-kit-examples[camel-kit-examples], and the Knowledge MCP server in
https://github.com/luigidemasi/camel-kit-knowledge[camel-kit-knowledge], each with its own version line. Issues
and pull requests go to the repository that owns the change; questions go to the Camel
link:/community/mailing-list/[mailing lists]. Contributors follow the
https://www.apache.org/foundation/policies/conduct.html[ASF code of conduct].

[[build]]
== Building

You need Java 17 or later, JBang, and Git; Maven comes with the wrapper. Always build with the wrapper, from the
repository root.

[source,bash]
----
./mvnw clean install                                      # all modules
./mvnw -B -Plinux-ship-certification clean install       # what CI runs (Linux)
./mvnw -B -Psourcecheck validate                          # the formatting gate
./mvnw test -pl camel-kit-core                            # one module
./mvnw test -pl camel-kit-core -Dtest=ShippedAssetStructureTest   # one test class

# run the CLI from source
jbang camel-kit-main/src/main/jbang/main/CamelKit.java --help
----

[cols="1,3"]
|===
| Module | Content

| `camel-kit-main` | The JBang entry point
| `camel-kit-core` | CLI commands, configuration, initialization and traits; all skills and templates as resources
| `camel-kit-graph` | The project graph: nine parsers and two post-processors
| `camel-kit-ship-resolver` | The classloader-isolated Maven resolver used for Ship evidence
| `camel-jbang-plugin-kit` | The Camel JBang plugin
|===

`distribution.properties` at the repository root is the single source of truth for every version pin; it is
copied into the JAR and never duplicated by hand. `tools/sync_distribution_mirrors.py` copies the few literals
Maven needs into the root POM and checks them with `--check`.

[[done]]
== Definition of done

A change is finished when all of the following hold:

* The tests of every touched module pass, and `./mvnw clean install` from the root passes when the change spans
  modules or touches skills, templates or `distribution.properties`.
* `./mvnw -Psourcecheck validate` passes.
* A skill, template or trait change passes `ShippedAssetStructureTest`, and the active documents pass
  `ResourceConsistencyTest` (see xref:architecture.adoc#equalization[the contract tests]).
* Every new skill is registered in the workflow manifest; a user-invocable one also in the templates of all eight
  agents and in the command reference.
* No version is hardcoded where `distribution.properties` applies.
* The documentation is updated, and `CHANGELOG.md` for significant changes.
* Nothing was skipped, disabled or weakened to get a green build; a failing check is reported, not hidden.

Branches are named `feature/...`, `fix/...`, `docs/...`, `command/...` or `template/...`. Rebase on `main` before
opening a pull request, fill in the template, link the related issues and request a review. Commit messages are
plain and descriptive.

[[skills]]
== Adding a skill

A skill is a directory under `camel-kit-core/src/main/resources/skills/` with a `SKILL.md` manifest (YAML front
matter with `name`, `description` and `user_invocable`, then the steps and a guide table) and a `guides/` directory
of instruction files loaded on demand. Every skill is registered in the workflow manifest
`camel-kit-workflow.yaml`, which drives the generated command stubs, the trait application and the structural tests:
a user-facing skill with its `generated_command`, documented in the command reference; an internal skill with
`status: internal` and `generated_command: null`, referenced from the guide table of the skill that dispatches it. Shared
guides under `skills/shared/` feed several skills, so check every caller before editing one. Agent-specific
behaviour goes into trait files under `templates/traits/<agent>/`, which need no code registration. See
xref:skills.adoc[] for the structure and the tiers.

[[docs]]
== Documentation

This site is built from `docs/antora.yml` and `docs/modules/` in the repository with Antora, as a component of the
Apache Camel website; edit the `.adoc` pages there and keep versions in the attributes of `antora.yml`. The
repository also keeps `docs/commands.md`, `docs/architecture.md` and `docs/constitution.md`, which the consistency
tests read, and `docs/user-guide.md`; keep them in step with these pages when behaviour changes.

[[release]]
== Releasing

Camel Kit follows semantic versioning. A release tag carries fixed POM versions and `main` carries the next
snapshot: release {camel-kit-version} is followed by {camel-kit-snapshot-version}.

IMPORTANT: Release {camel-kit-version} was published before the donation, with the direct publication workflow that
the repository still carries in `docs/releasing.md` and `.github/workflows/release.yml`. As an Apache Camel
subproject, Camel Kit releases follow the https://www.apache.org/legal/release-policy.html[ASF release policy]: a
release candidate is staged and verified, and the PMC votes on it, with at least three binding +1 votes, before
anything is published. The Camel xref:manual::release-guide.adoc[release guide] describes that sequence. The
workflow below deploys straight to Maven Central without staging or a vote, so it is not the Apache procedure; the
automation and this page are updated when the first Apache release is prepared.

The preparation steps from `docs/releasing.md` remain the mechanics of cutting a version:

. From reviewed `main`, on a release branch, update the README, the changelog and the documentation; keep Ship
  labelled Technology Preview.
. Set the reactor version and the root SCM tag, pin `knowledge.mcp.version` in `distribution.properties` to the
  published Knowledge release, and synchronize the JBang launcher fallbacks with
  `./mvnw -B -N antrun:run@sync-jbang-launcher-versions`.
. Run the full release build with artifact signing:
  `./mvnw -B -Prelease,sourcecheck,linux-ship-certification clean install`.
. Review the diff, commit with a signed commit, tag that exact commit and record its SHA.
. Advance every POM to the next snapshot, restore the SCM tag, synchronize the launchers again, validate the
  development build, sign the commit and open the pull request.

The Knowledge MCP server and its refreshed index are released first, and the pinned runner artifact is verified
before Camel Kit is built. After a release, the tag-pinned JBang install and the Camel JBang plugin are verified from
a clean cache, and the unqualified JBang alias keeps following the development branch.
