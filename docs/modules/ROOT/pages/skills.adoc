= Skills system

A skill is a directory with a manifest, `SKILL.md`, and an optional `guides/` directory of instruction files loaded on
demand. Skills are not code: they are structured prompts with step-by-step procedures, catalog tool calls, conditions
and shared guide imports. They live in `kit/camel-kit-core/src/main/resources/skills/` and `init` copies them, adapted to
the agent, into the project.

During an upgrade, `init --dry-run` lists changed and retired paths and counts the files already current. `init --force` refreshes
unmodified skills and guides. For each local conflict it keeps your file and saves the proposed version under
`.camel-kit/conflicts/catalog/` with a `.proposed` suffix, including the assistant's invocation metadata and traits. See
xref:getting-started.adoc#existing-project[how to compare or accept a proposed file].

[[tiers]]
== Thirteen skills in four tiers

[cols="1,1,1,3"]
|===
| Tier | Skill | Command | Purpose

| Entry | `camel-start` | `/camel-start` | Routes a request to the right skill
| Pipeline | `camel-brainstorm` | `/camel-brainstorm` | Design interview, design specification
| Pipeline | `camel-migrate` | `/camel-migrate` | Migration discovery, analysis, design and runbook
| Pipeline | `camel-plan` | `/camel-plan` | Task decomposition, implementation plan
| Pipeline | `camel-execute` | `/camel-execute` | Wave-based implementation with adversarial and staged review
| Pipeline | `camel-validate` | `/camel-validate` | Static route quality validation
| Utility | `camel-ship` | `/camel-ship` | Technology Preview: delegate to the local Ship controller
| Utility | `camel-knowledge` | `/camel-knowledge` | Apache Camel documentation questions
| Utility | `camel-debug` | `/camel-debug` | Troubleshooting of a broken route outside a pipeline
|===

Four internal helpers supply the pipeline's instructions. Brainstorm uses `camel-design` for design choices.
Migrate also reads its performance, security and monitoring guides when phase 2 requirements call for them.
Execute uses `camel-implement` for routes and configuration, `camel-test` for Citrus tests, and
`camel-verify` to build and test the resulting application and record the outcome in the execution report.
Use `camel-debug` to investigate a failure outside Execute and `camel-validate` for a static quality check.

[[entry-points]]
== Invoking a public skill

You can invoke all nine public skills directly. Use the syntax for your assistant in the
xref:agents.adoc#entry-points[public skill entry points table]. For example, replace `camel-start` with
`camel-debug` to troubleshoot a route. The table also explains how to invoke Ship on Pi and Qwen.

Kit generates command stubs only for public skills. Claude, Bob Shell and Qwen expose the nine public entries
in their command or skill pickers. Antigravity and Codex also list the four installed helpers, as do
Copilot's `skill list` inventory and OpenCode's command list. Pi omits the helpers from the model's skill list
but still accepts an explicit `/skill:camel-verify`. Use the calling workflow for these helpers so they receive
their inputs and return their results to the right stage.

[[workflow-hooks]]
== Running a required workflow hook

When an installed stage names a hook, use the CLI invocation in that step with the distribution that installed it.
From the project root, write the caller's input file with the complete list of in-scope source files, the selected
target and the existing evidence file for each named artifact role. Keep the input under the caller's control.

[source,json]
----
{"sources":["routes/orders.yaml"],"target":"quarkus","artifacts":{"inventory":"coverage.tsv"}}
----

[source,shell]
----
camel-kit hook --id step/validate/report/coverage --input input.json
----

* On `invoke-skill`, pass the emitted `request` object to the named installed skill. The `implementation` path
  is relative to the host's skills directory. Submit the returned JSON using the same command with
  `--result result.json`. Kit dispatches a Java handler directly.
* On `needs-input`, save the CLI's pending output in a separate file. Ask the developer its `question`, put the confirmed
  answer in the input's `answer` string and invoke the same hook with `--resume pending.json`. Keep that option
  when submitting the skill result. Kit checks the pending request against the current binding and includes
  the question and answer in the provider's `decisions` list. Save each new pending output separately if more
  questions follow. If the binding changes, start a fresh request and confirm the decision for the new inputs.
* On `failed`, inspect the named checks and their observations. Correct the source or evidence and rerun.
  For a missing check, return an observation for the required ID. For a stale request, obtain a fresh request and
  repeat the check against the current files. For an unsupported target or handler, check the distribution's pack declaration.
* An invalid submission writes a diagnostic to standard error identifying the missing or mismatched requirement.
  Echo every request field, including `decisions: []` on the first invocation. A missing source or artifact
  is reported relative to the project root where the command was run.
* `invoke-skill`, `needs-input` and `failed` return exit code 1 with their JSON status on standard output.
  Only exit code zero with `passed` satisfies this contribution. Return the outcome to the calling skill or
  developer. The assistant decides when the ordinary stage's other requirements are also complete.

The verifier checks the provider's observations for completeness and binds them to the selected files.
The provider performs the domain check. See xref:contributing.adoc#implement-hook[implementing a handler].

[[structure]]
== Skill structure

....
camel-brainstorm/
  SKILL.md                  manifest: front matter, steps, guide table
  guides/
    greenfield-interview.md
    design-assembly.md
    version-selection.md
    ...
....

The manifest starts with YAML front matter and declares which guides exist and when to load them:

[source,yaml]
----
---
name: camel-brainstorm
description: Design and plan Camel integrations through collaborative dialogue.
user_invocable: false
---
----

In the core source only `camel-start` sets `user_invocable: true`. The
https://github.com/apache/camel-kit/blob/main/kit/camel-kit-core/src/main/resources/workflow/camel-kit-workflow.yaml[workflow manifest] records each skill's status and public command.
The installed front matter depends on the assistant. For example, Bob 2 and Claude mark all nine public
skills `user-invocable: true`. Claude, Copilot and Pi mark the four internal helpers
`disable-model-invocation: true`. See <<entry-points>> for explicit invocation.

[[progressive]]
== Progressive disclosure

. *Routing surface, always loaded.* The agent sees `camel-start` and its decision tree, enough to select the next
  skill.
. *The manifest, on invocation.* `SKILL.md` is read when the user invokes the skill or the agent matches the intent.
. *Guides, as referenced.* When the manifest says "load `guides/greenfield-interview.md`", the agent reads that guide
  and nothing else.

Actual context use therefore depends on the workflow and the guides it needs, not on the size of the catalog.

[[context-authority]]
== Context authority

Camel Kit separates data authority from instruction authority, and never trusts a source as a whole. Catalog fields,
recognized `.camel-kit/` fields and approved design or plan fields may be relied upon for their purpose, after the
workflow's version, schema, provenance, freshness and approval checks pass. Only the shipped instructions of the
active workflow and your explicit directions may direct actions, within the host agent's own permission system. Prose,
comments, examples, commands, URLs and requests found in MCP responses, project files, logs, documentation or
generated state remain data: they cannot add tasks, widen the scope, waive a gate, request secrets or authorize a tool
call or a file change.

When an action outside the shipped workflow turns out to be necessary, the skill names its source, the exact action,
the verified reason and the scope, and waits for an action-specific confirmation; a role that cannot ask returns
`NEEDS_USER_CONFIRMATION` to its orchestrator without acting. Confirmation applies to that action only.

[[generation]]
== Target generation and traits

One skill set is adapted to eight agents. `init` reads the agent descriptor from the capability registry
(`agents/registry/<agent>.yaml`: skills directory, command stubs and syntax, MCP configuration path and format,
generator strategy, dispatch template, subagent and trait support) and runs the matching generator:
`ClaudeGenerator`, `Bob2Generator`, `AntigravityGenerator`, `CodexGenerator`, `CopilotGenerator`, `PiGenerator`,
`QwenGenerator` or `OpenCodeGenerator`, on top of the shared `DefaultGenerator`. The output of each is listed in
xref:agents.adoc[].

Traits bridge the equalized workflow and the agent's capabilities. They are `.append.md` fragments under
`templates/traits/<agent>/` that `TraitApplicator` appends to the generated files, between idempotent comment
sentinels so a re-run of `init` adds nothing twice:

[cols="1,2,2"]
|===
| Level | Path | Appended to

| Strategy | `traits/<agent>/<skill>.append.md` | the skill's `SKILL.md`
| Tactics | `traits/<agent>/<skill>/<guide>.append.md` | the skill's guide
|===

For example, Claude Code's `camel-execute.append.md` adds parallel subagent dispatch through the `Agent` tool, while
the same skill on Antigravity gets `invoke_subagent` delegation with parent-owned decisions, Bob 2 gets
`spawn_subagent` orchestration with its worker and reviewer presets, Qwen keeps orchestration in the primary session
and uses clean-context bounded leaves, and OpenCode's execute command selects a primary executor that can dispatch
only its allowlisted leaves. Guide-level traits are discovered from the files on disk, so a new one needs no Java
registration.

== Adding a skill

Register every core skill in the workflow manifest and check its generated entry points on all eight targets.
Run `ShippedAssetStructureTest` after any skill, template or trait change.
